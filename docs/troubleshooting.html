排错建议

排查 FtpPool 问题时，先做这三件事：

  1. 看异常类型：FtpException.getType() 已经帮你把失败分了类（见下表）。
  2. 看池快照：pool.stats() 的 active / idle / pending / borrowTimeouts。
  3. 开日志：把 io.ftppool 设为 DEBUG，LoggingFilter 会打印带 pool/connectionId/operation/duration/exceptionType 的上下文。

异常类型速查

所有失败都继承自 FtpException（非受检），携带 FtpExceptionType。分类决定连接是「销毁」还是「回池」。

FtpExceptionType含义连接处置
CONNECTION物理控制/数据链路断开（socket reset、EOF、disconnect）销毁
AUTHENTICATION登录 / 凭据失败销毁
VALIDATION校验失败（如 NOOP 失败）销毁
TIMEOUT连接 / socket / 数据传输超时回池
PROTOCOL协议层错误（非预期响应、非法时序）回池
TRANSFER数据传输失败（RETR/STOR）回池
BUSINESS业务层 FTP 应答失败，连接仍可用回池
POOL_TIMEOUT借出等待超过 connectionTimeout（未拿到连接）不涉及
POOL_CLOSED对已关闭的池执行操作不涉及

判定规则：CONNECTION / AUTHENTICATION / VALIDATION，或底层直接抛出 IOException，都会让连接 markBroken 并在归还时销毁。其余类型保留连接以便复用。

常见现象 → 原因 → 处理

现象可能原因处理
抛 POOL_TIMEOUT（Timeout while borrowing） 池已满且无空闲连接，或单次操作太慢长期占用连接 看 stats().pending() / borrowTimeouts；提高 maxSize、缩短操作耗时、检查是否泄漏未归还。
应用刚启动就报 No FtpConnectionFactoryProvider ... supports ... classpath 缺少适配器 加入 ftp-pool-adapter。
启动报 No PoolEngineFactory named 'fast'/'commons' ... classpath 缺少对应引擎模块 加入 ftp-pool-engine-fast 或 ftp-pool-engine-commons。
构建池时报 No FtpFilterProvider named 'full' ... 用了 hybrid()/monitor() 但缺少可观测性模块 加入 ftp-pool-observability，或改用 observability=NONE 的 fast()。
Spring Boot 启动失败：spring.tidepool.ftp.host is not configured 启用了池但没配 spring.tidepool.ftp.host 配置 spring.tidepool.ftp.host，或 spring.tidepool.ftp.enabled=false，或提供自定义 FtpPool Bean。
认证失败 AUTHENTICATION 用户名/密码错误、服务器要求 FTPS、账户被锁、IP 白名单 核对凭据；确认是否需要 FTPS_EXPLICIT；查服务器端认证日志。
连接被服务器「静默断开」后批量失败 NAT / 防火墙闲置超时切断了控制连接 调小 maxLifetime（如 5m）与 idleTimeout，让连接在被切断前回收。
偶发 CONNECTION（socket reset / EOF） 服务器重启、网络抖动、服务端主动断开 属正常可恢复失败：连接会被销毁，下一次 borrow 重建。用指标观察频率，必要时重试业务层操作。
传输超时 TIMEOUT 大文件 / 慢链路，dataTimeout 太小；被动模式端口被防火墙拦截 调大 dataTimeout；确认服务器被动端口范围已放行。
日志出现 Possible connection leak 业务借出后忘记 release，或没用 execute() 按日志中的 borrowThread 与 trace 定位；改用 pool.execute(...) 自动归还。
日志出现 Slow operation 操作耗时超过 slowOperationThreshold 结合 ftp.operation.latency / ftp.operation.slow 定位操作类型；必要时调阈值。
文件内容乱码 / 中文名异常 服务器与控制通道编码不一致 显式设置 encoding("GBK") 或与服务器匹配的编码（默认 UTF-8）。
归还后连接被销毁（销毁数持续增长） reset 失败（工作目录/文件类型恢复不了），或超过 maxLifetime 这是保护机制。若频率过高，检查服务器对 CWD / TYPE / PASV 的支持与稳定性。
rename / makeDirectory 抛 UnsupportedOperationException 自定义后端未实现该操作 Apache Commons Net 适配器已支持；若替换了适配器需自行实现。
FTPS 证书 / hostname 校验失败 证书不被 JVM 信任库信任，或 CN/SAN 与 host 不符 配置自定义 trustManagers；确认 host 与证书一致。详见 FTPS 指南。不要用 trust-all 绕过。

连接问题排查清单

先确认池的状态

FtpPoolStats s = pool.stats();
System.out.printf("total=%d active=%d idle=%d pending=%d borrowTimeouts=%d validationFailures=%d%n",
        s.total(), s.active(), s.idle(), s.pending(), s.borrowTimeouts(), s.validationFailures());
  • active == maxSize 且 idle == 0 且 pending > 0 → 容量不足。
  • active 长期接近 maxSize 但 QPS 不高 → 疑似泄漏，看泄漏告警。
  • validationFailures 持续增长 → 连接在被复用前已失效，考虑调小 maxLifetime/idleTimeout。

再确认网络与服务器

  • 用系统 FTP 客户端（或 curl ftp://...）验证主机、端口、凭据本身可用。
  • 被动模式：确认服务器 PASV 端口范围在防火墙放行；必要时联系运维开放。
  • FTPS：确认协议类型（explicit vs implicit）与端口匹配；确认数据通道保护。
  • 时钟与证书有效期：证书过期会表现为 TLS 握手失败。

打开详细日志

日志框架中把 FtpPool 调到 DEBUG（Spring Boot 的 application.yml 示例）：

logging:
  level:
    io.ftppool: DEBUG

编程式构建时，可加一个详细的 LoggingFilter：

import io.ftppool.observability.LoggingFilter;

FtpPoolProfiles.hybrid()
        .host("ftp.example.com")
        .addFilter(new LoggingFilter(true))   // verbose：记录每次转换
        .build();

即使开启 DEBUG，日志中也不会出现密码：凭据从不进入日志上下文、指标或 JMX。 如果怀疑密码错误，请通过配置来源本身排查，而不要期待从日志里看到它。

仍然无法定位？

  • 对照 配置参数 确认每个参数是否被意外覆盖（尤其是 Spring Boot 的 mode 与逐轴覆盖）。
  • 看 可观测性 中的指标与 JMX，用数据判断是容量、网络还是业务问题。
  • 用 stats() + 异常 type + 日志三者交叉验证，通常足以区分「池问题」与「服务器/网络问题」。
